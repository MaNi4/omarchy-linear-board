# Development

How the plugin is organized, how it talks to Linear, and how to test it.

## Code layout

The plugin has three entry points, listed in `manifest.json`:

- `Board.qml` is the board window (an Omarchy overlay). It holds what the whole board shares: the connection to
  Linear, the team's data, filters, the cursor and the theme.
- `BarWidget.qml` is the bar icon with the unread count and the running timer.
- `Service.qml` registers the global shortcuts in Hyprland (with `Hotkey.js`).

Inside the board:

- `ui/` contains what's drawn: the board and list (`BoardView`, `BoardHeader`, `BoardColumn`, `IssueCard`,
  `ListGroup`), the issue editor (`IssueEditor` and its parts), settings, the time report, inbox, search, command
  palette, project overview, shortcut help, toasts and small shared components.
- `logic/` contains the behavior, one part per file: `Sync` (loading data, the offline queue), `IssueOps`,
  `EditorOps` and `EditorState` (the issue being edited), `InboxCtl`, `TimeTracker`, `SharedFolder`, `Lists`,
  `Undoer`, `Uploads`, `Workspace`, `Commands`, `ProjectOps`, `Pickers`, `Bulk` (including drag and drop),
  `Keyboard` and `Notices` (toasts and desktop notifications).

Every file in `ui/` and `logic/` is created inside `Board.qml`. It reaches the board's state through the id `root`
and the other parts through their ids (`sync`, `issueOps`, `ed`…).

The plain JavaScript files hold logic without QML, so the tests can run them in Node:

- `Linear.js`: everything sent to Linear's API and how the answers are read (queries, mutations, filters,
  Linear's fixed values, error messages).
- `Issues.js` (columns, filters, sorting, moving cards), `Edit.js` (what an edit sends and how it's undone),
  `Recur.js` (recurring issues), `Inbox.js` (inbox filters and the bar's state), `Markdown.js`, `Dates.js`,
  `Time.js` (time entries), `Shared.js` (shared settings, export and import), `Help.js` (shortcut help) and
  `Hotkey.js` (global shortcuts).

`bin/linear-notify` sends desktop notifications over D-Bus. It reads them from stdin, so issue titles never show up
in the process list, as they would with `notify-send` arguments.

## Talking to Linear

All requests go through `gqlWith` in `Board.qml`. A few things there aren't obvious:

- **Timeouts.** A request without an answer is given up after 30 seconds. Changes that fail this way (or because
  there's no network) go to the offline queue in `~/.cache/omarchy-linear-board/outbox.json`.
- **No duplicates.** A new issue or comment carries an id generated by the board. If the answer was lost but Linear
  did create it, sending it again fails with a conflict, and the board looks up the existing one instead.
- **Order of changes.** While changes wait in the queue, new ones are queued behind them, and changes to one issue
  are sent one at a time. A request the board gave up on can still reach Linear later, after a newer change. So the
  board checks the issue 15 seconds, 1 minute and 3 minutes after sending the queue, and sends the newer values again
  if an older one won.
- **Sleep and network changes.** Qt doesn't close a connection when a request on it is aborted, so after a suspend
  every request can hang on a dead connection. The board notices waking up (a gap between timer ticks) and gives
  up on requests after 8 seconds for a minute. After a hung request, it sends requests through `curl`, which opens
  a new connection each time, for the next 15 minutes. Loading a team that got no answer is retried after 2, 5 and
  10 seconds.
- **Rate limit.** On HTTP 429 or the `RATELIMITED` error, no request goes out until Linear's reset time (at most an
  hour). Changes wait in the queue.
- **Internal inbox fields.** The inbox uses fields Linear marks as internal (unread count, grouping, titles). If
  Linear removes them, the inbox switches to public fields and builds the same rows itself.

The board checks the inbox every minute, also while its window is closed, and writes the result to
`$XDG_RUNTIME_DIR/omarchy-linear-board/inbox.json` for the bar icon. The icon dims when that file is more than
5 minutes old.

## Tests

Install the `graphql` package once, then run the tests:

```bash
npm install
npm test
```

`npm test` runs anywhere and covers:

- `tests/helpers.test.js`, `time.test.js`, `shared.test.js`, `hotkey.test.js`: the plain JavaScript helpers.
- `tests/refs.test.js`: every `Linear.x`, `Issues.x`… used in QML or JS exists and is imported.
- `tests/members.test.js`: every `root.x`, `sync.x`… one part of the board uses exists in that part.
- `tests/api.test.js`: every query and mutation, and the inputs the board builds, checked against Linear's
  published schema. It fails when something is removed or deprecated. With `LINEAR_SCHEMA=live LINEAR_API_KEY=…`
  it uses the live API's schema instead.

### End-to-end tests

These need an Omarchy machine. They run the board in a separate, invisible Quickshell instance with its own
temporary files, so nothing appears on your screen and nothing touches your Linear account or your files.

```bash
npm run test:e2e
```

- `tests/e2e/run.js` (32 scenarios) runs the board and the bar icon against `tests/fake-linear.js`, a fake Linear
  API with test data. The fake server can drop, delay or refuse requests, which covers the offline queue, rate
  limits, timeouts, broken answers, a wrong or revoked key, the inbox fallback, paging and a simulated suspend.
  Pass a name filter to run only some scenarios: `node tests/e2e/run.js inbox`.
- `tests/e2e/shared.js` (6 scenarios) runs two boards as two computers with a shared folder: time and settings
  reach the other computer, Syncthing conflict copies are merged, and a recurring issue is created once.

To try the board against the fake server yourself, start `node tests/fake-linear.js`, then start a shell with
`LINEAR_BOARD_ENDPOINT=http://127.0.0.1:47123/graphql LINEAR_API_KEY=lin_api_fake`. Only addresses on this machine
are accepted.

### Tests against the real API

`tests/e2e/live.js` runs against Linear itself, in a project you keep for testing. Everything it creates is named
`[bt] …` and deleted at the end. Your inbox is only read.

```bash
LINEAR_TEST_PROJECT=<project id> node tests/e2e/live.js
```

Requests go through a local proxy that can drop, delay or refuse them, so the offline and timeout cases run against
Linear's real answers. `LIVE_CURL=1` sends every request through `curl`, and `LIVE_DIRECT=1` skips the proxy.

### Screenshots

```bash
npm run screenshots
```

This recreates `preview.png` and `screenshots/` from the fake server's demo data, in your current Omarchy theme.

### CI

GitHub Actions runs `npm test` on every push and every morning, so a change in Linear's API fails a run and GitHub
emails you. With a `LINEAR_API_KEY` repository secret, it also checks the live schema and that Linear still answers
the internal inbox fields. A read-only key limited to one team is enough.
